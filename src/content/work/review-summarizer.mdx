> **Note on scope.** This project is not live. The scraper depends on Google
> Maps page structure, which changes without warning, so a public deployment
> would break unpredictably. I have kept it here because the engineering and
> the reasons it is not deployed are both worth explaining.

## Context

A restaurant with a few hundred Google Maps reviews has a real problem: the
information is there, but nobody reads it. An owner sees a star rating and the
five most recent comments, and everything else is buried.

I built a tool that takes a restaurant, collects its reviews, classifies their
sentiment and produces a summary with a word cloud of recurring terms.

## The problem

A star rating compresses everything into one number. A 4.2 tells you almost
nothing actionable: it does not distinguish a restaurant with consistently good
food and slow service from one that is excellent at lunch and poor at dinner.

The detail lives in the text, and text does not aggregate by itself. I wanted to
answer a specific question: **what do people repeatedly complain about, and what
do they repeatedly praise?**

## My role

Solo, across three repositories:

- **Backend** (Python, FastAPI) with the scraping and ML pipeline
- **Frontend** (JavaScript) for submitting a restaurant and viewing results
- **API** as a thin deployable service layer

## Technical decisions

### Layering the backend by concern

Rather than one script, I structured the backend so each responsibility is
isolated:

```
app/
├── api/endpoints/    reviews.py, scraping.py
├── core/             configuration
├── ml/               summarizer.py, wordcloud_generator.py
└── scrapers/         gmaps_scraper.py
```

This mattered more than it looks. The scraper is the fragile part; the ML and
API layers are stable. Keeping them apart means the scraper can be swapped for
an official API without touching anything else, which is exactly the change I
would make if I returned to this.

### Splitting the model out of the repository

The trained sentiment model is a large binary. Committing it would bloat the
repository and make every clone slow, so the README links to it separately.

That is the right instinct, but the wrong implementation. Model artifacts
belong in something like DVC or a release asset, not a personal Drive link. The
current setup means the project cannot be reproduced if that link ever dies.

### Scraping, and why it was the wrong foundation

Google Maps has no free public reviews API at any useful volume, so I scraped.
It worked, and the whole project depends on that choice in a way I underestimated.

A scraper is coupled to a page structure that a company you do not control can
change at any time. That is fine for a coursework project with a fixed deadline
and fatal for anything that has to keep running. This is the reason the project
is not deployed.

## The hardest problem

Sentiment classification on **Indonesian restaurant reviews**, which are messier
than the clean English datasets most tutorials assume.

Real reviews mix Indonesian and English in one sentence, use heavy regional
slang and abbreviations, and rely on context that flips meaning entirely. A
short review saying the portion is small is negative for value and neutral for
someone dieting. Sarcasm broke the classifier constantly.

I improved it with preprocessing tuned for the actual language: normalising
common slang, handling mixed-language tokens, and stripping the emoji noise that
was polluting the feature space. It got usefully better without ever getting
genuinely good.

The honest conclusion is that a bag-of-words approach is the wrong tool for
informal Indonesian. A transformer fine-tuned on Indonesian text, IndoBERT for
example, would handle context and negation properly. I did not have the compute
budget at the time, and I chose to ship something working over something stalled.

## Outcome

- A working pipeline from a restaurant name to a sentiment breakdown and word cloud
- A backend structure clean enough that the fragile part is genuinely replaceable
- A clear understanding of where the approach breaks

## What I would do differently

**Do not build on a scraper.** The dependency on someone else's page structure
is the single reason this is not live. Google Places API has real costs and real
quotas, but it has a contract, and a project that can only run on my machine is
not finished.

**Use a language model suited to the language.** Fine-tuning IndoBERT would deal
with the code-switching and negation that defeated the classical model.

**Version the model artifact properly.** A Drive link is not reproducibility.
DVC or a tagged release would make the project clonable years from now.
